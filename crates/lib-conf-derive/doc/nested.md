# Nested `Config` structs

A *nested* `Config` struct field is one whose type also derives `LibConfig`.
The `#[config(nested)]` attribute is used to communicate this.

Fields marked `nested` have some unique handling and behaviours, as described below.

## Changes to `Override` struct

When the `nested` attribute is set, the field type in `OverrideConfig` will automatically be mapped to the nested field's corresponding `Override` type.

For example, this `Config` definition:

```rust,ignore
#[derive(LibConf, ..)]
pub struct NyConfig {
    #[config(nested, ..)]
    child: ChildConfig,
}
```

Will result in a generated `MyOverrideConfig` resembling:

```rust,ignore
// generated by LibConf derive
pub struct MyOverrideConfig {
    child: Option<ChildOverrideConfig>,
    //            ^^^^^^^^^^^^^^^^^^^ Mapped from `ChildConfig`
}
```

> **Note:**
>
> Manually specifying the `Override` type used for the nested field will be added in a future release.
>
> This would prevent issues when the nested config comes from a crate that may depend on a version of `lib-conf` with different naming standards.

## Changes to `Builder` struct

The generated `Builder` struct observes the following changes:

1. The visibility of the field's setter will be dropped from `pub` to `pub(crate)`
   - See the [Setter visibility drop](#setter-visibility-drop) *Background* section for an explanation
   - This behaviour can be reverted with the [`nested(pub_setter)`](#nested_pub_setter) attribute
2. The setter functionality is instead provided by a new `{field}_builder()` method
   - If the nested `Config` has a `Default` impl, a `{field}_builder_default()` method is also added

If the `nested` field type is `Option<_>`, there are additional, **significant** caveats to consider.
See the [Merging `OverrideConfig` into `Config`](#merging-overrideconfig-into-config) section for more information.

The substituted builder setters are described below.

### Builder closures

#### `{field}_builder()` method

When initializing a `Config` struct using its builder, nested fields can be configured with a closure using the corresponding `{field}_builder()` method.

For example, initializing `MySdkConfig` which contains a nested `api: ServiceConfig` field:

```rust,ignore
let sdk_config = MySdkConfig::builder()
    .logging(true)
    .api_builder(||
        ServiceConfig::builder("https://example.com") // endpoint is a required field
            .client_id("0")
    )
    .build();
```

#### `{field}_builder_default()` method

If the nested `Config` (and `Override`) structs have `Default` impls (indicated using the [`nested(default)`](#nested_default) attr),
a `{field}_builder_default()` method will also be provided.

This provides the same functionality as the previously described method, except the `Builder` is pre-populated using it's `Default` impl and passed to the closure as a parameter.

Continuing from the same example as above, this time assuming the `endpoint` field is optional:

```rust,ignore
let sdk_config = MySdkConfig::builder()
    .verbose(true)
    .api_builder_default(|api| api
        .endpoint("https://example.com")
        .client_id("0")
    )
    .build();
```

As can be seen, the default method is considerably cleaner and should be preferred where applicable.

Standard field merging works by assigning over (replacing) the config field when the `Override` field is set.

This behaviour differs for nested `Config` fields, which operate closer to an *upsert* than an *overwrite*.

---

The method used to merge nested `Override` fields is largely dependent on whether or not the corresponding `Config` field is optional - and additionally - the precise mechanism used to do so.

`Config` fields communicate their required/optional constraint in one of three ways:

1. The field is of type `T` (non-`Option`) and it **does not** have a `default` assignment attr. It is therefore **required**
2. The field is of type `T` (non-`Option`) and it has a `default` assignment attr.  It is therefore **optional**
3. The field type is `Option<T>`, and is therefore **optional**

**For cases #1 and #2:** merging the nested field **is trivial**.

Since `config.nested` is always present (due to being required or by having a default),  merging recursively works, e.g:

```rust,ignore
config.nested.merge_with_override(override_conf.nested);
```

Or, identically:

```rust,ignore
config.nested += override_conf.nested
```

**For case #3**, where the type is `Option<T>`, merging is **significantly more convoluted** (to a degree *near comical*).

This topic has earned it's very own section

## Merging into `Option<Config>`

Since the `Config` struct's `nested` field could, at any given time, be `None`, the recursive `merge_with_override` strategy is no longer viable for the following reasons:

1. `None.merge_with_override(..)` isnot valid
2. Unlike most encounters with `Option<_>`, a simple `if let Some(nested) = config.nested { /* merge.. */ }` is not suitable
   - The inner `merge` would only be called if the nested value was explicitly initialized using the builder
   - If a user configures the nested fields at runtime (into an `Override` struct) and does not use the builder, the `Override`-provided field would just be dropped silently.
     - This is certainly undesired behaviour

To allow merging a nested `OverrideConfig` struct into an `Option<Config>` field, the nested `Config` struct must be able to initialize itself from its `OverrideConfig` - covering the case where the parent's `Option<Config>` field is `None`.

You may be thinking:

> A `From<OverrideConfig>` impl for `Config` would be a great fit here

I totally agree!

---

### `From<OverrideConfig>` for `Config`

`lib-conf` will automatically implement `From<OverrideConfig>` for `Config` if possible.

This will be possible if every `Config` field meets the following conditions:

- A standard field (non-nested) must have:
  - An `Option<_>` type, or
  - A `default` attribute, or
  - An `override_required` attribute (guarantees the corresponding `OverrideConfig` is present/non-`Option`)

-  A nested `Config` field must either:
  - Meet any of the above standard field conditions, or
  - Have `From<OverrideConfig>` impl'd against its respective `Override` struct type
    - This is indicated using the `nested_from_override` attribute on the `nested` field

In other words: all fields must either be optional, have their override counterpart required, or - if the field is a nested config - it must also impl `From<Override>`.

This allows for hierarchical, nested `Config` structs - but fundamentally requires that all non-root `Config`s have all optional fields.

**But what if the nested config *does* have required fields?**

Using an `Override` struct to initialize a `Config` struct that has required fields could fail if any of those fields weren't provided in the `Override` config.

Given the inherent fallibility introduced, we intuitively reach for `TryFrom<OverrideConfig>` as the alternative.

--

### `TryFrom<OverrideConfig>` for `Config`

If `From<OverrideConfig>` can't be implemmented (as above), `lib-conf` will instead implement `TryFrom<OverrideConfig>` if possible.

There is only 1 scenario where this *isn't* possible:

- A field is required (no `default` attr, non-`Option<_>`) **and** has the `override_skip` attribute set

<div class="warning">
<h3>Warning</h3>
Due to the above, using <code>override_skip</code> on a non-optional nested <code>Config</code> <b>should be avoided at all costs</b>.

If used, your <code>Config</code> struct <b>cannot be nested in any capacity</b>, regardless of provided workarounds.

This is true for not only your crate, but for <b>-<i>everyone</i> that depends on your library</b> as well.
</div>

## Background

### Setter visibility drop

Dropping the `Builder` setter visibility of `nested` fields may seem strange at first. However, there are 2 important notes to consider:

1. The behaviour of the setter remains unchanged
   - It will expect a `Config` struct as its parameter, and therefore must *already be built*.
2. The [`build()`] method, which merges any provided `OverrideConfig` in, automatically handles merging of the nested field's `Override` counterpart.
   - Therefore, it is not required to call [`with_override()`] on any `Builder`s whose output will be nested.

These 2 behaviours can make working with large `Config` trees unavoidably messy.

More importantly, the standard setter requires consumers to construct their own builder (for which they'll later need to call `build()` on).
It's highly likely they will be inclined to call `with_override` on the builder prior to calling `build()`, mirroring the pattern used in the main `Config`. This won't be possible, however, as they will lack access to the underlying `Override` field due to it's `pub(crate)` visibility.

These stack into a ***very* poor UX**.
